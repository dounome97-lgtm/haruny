# 프로젝트 개요

## 제품 방향

이 프로젝트는 학생과 부모가 매일 사용하는 생활형 코치 앱을 지향한다.
내부 데이터 구조와 운영 로직은 정확해야 하지만, 사용자에게 보이는 화면은 관리자 페이지나 백오피스처럼 보이면 안 된다.

핵심 경험은 사용자가 앱을 열었을 때 3초 안에 다음 질문에 답을 얻는 것이다.

- 지금 무엇을 해야 하는가?
- 아직 오늘 계획을 끝낼 수 있는가?
- 쉬어도 되는가, 바로 시작해야 하는가?
- 늦어졌다면 어떻게 회복할 수 있는가?

또 하나의 핵심 경험은 장기 목표를 학생이 감당할 수 있는 오늘의 행동으로 쪼개는 것이다.
시험, 수행평가, 꾸준한 암기 루틴 같은 장기 계획은 월간, 주간, 일간 계획으로 내려와야 하며, 학생 화면에서는 결국 `오늘 지금 할 일`로 보이도록 한다.

## 백오피스화 방지 원칙

다음 원칙은 모든 화면 설계, 기능 구현, Codex 작업 지시에서 항상 우선한다.

- 첫 화면에 테이블, 검색 필터, 엑셀식 목록을 두지 않는다.
- 첫 화면을 `관리`, `등록`, `수정`, `삭제` 중심으로 설계하지 않는다.
- 데이터 목록보다 현재 상태, 다음 행동, 남은 시간 판단을 먼저 보여준다.
- 사용자를 관리자가 아니라 생활 중인 학생 또는 안심하고 싶은 부모로 대한다.
- CRUD 기능은 필요하지만 메인 경험이 아니라 보조 흐름으로 숨긴다.
- 설정, 세부 편집, 통계, 로그는 1차 화면이 아니라 2차 깊이 이하에 둔다.
- 상태 배지와 관리 버튼을 많이 나열하는 화면을 기본값으로 삼지 않는다.
- 알림은 감시나 처벌이 아니라 회복을 돕는 코치 톤으로 작성한다.
- 부모 화면도 감시 대시보드가 아니라 안심 요약과 개입 필요 여부를 중심으로 구성한다.
- 학생 화면은 완료율보다 `지금 할 수 있는 가장 작은 다음 행동`을 우선한다.

## 모바일 앱 전환 전제

이 프로젝트는 초기 구현을 웹앱으로 시작하더라도, 최종적으로 모바일 앱 전환을 반드시 염두에 둔다.
웹앱은 제품 흐름과 계산 로직을 빠르게 검증하기 위한 1차 구현이며, 구조는 처음부터 모바일 앱으로 옮기기 쉽게 설계한다.

- 모든 화면은 모바일 우선으로 설계한다.
- 핵심 학습 계획 계산 로직은 UI 컴포넌트 안에 섞지 않고 별도 모듈로 분리한다.
- 장기 계획 생성, 하루 계획 계산, 알림 판단은 순수 함수 또는 서비스 계층으로 분리한다.
- 학생/부모 화면은 API 또는 서비스 인터페이스를 통해 데이터를 받는 구조로 만든다.
- 알림은 웹 푸시, 앱 푸시, 문자/카카오 알림으로 교체 가능하도록 추상화한다.
- 브라우저 전용 기능에 핵심 로직이 의존하지 않게 한다.
- PWA는 모바일 앱 전환 전의 중간 단계로 보되, 최종 목적지는 네이티브 또는 크로스플랫폼 모바일 앱이다.
- 웹에서 검증한 UX와 데이터 모델을 모바일 앱에서 재사용할 수 있게 화면, 로직, 데이터 경계를 분명히 둔다.

## 화면 설계 기준

화면을 만들기 전에 다음 질문에 답한다.

- 이 화면은 사용자가 관리하려고 보는가, 행동하려고 보는가?
- 첫 3초 안에 다음 행동이 보이는가?
- 이 목록은 지금 꼭 필요한가?
- 수정/삭제 버튼이 너무 빨리 노출되어 있지 않은가?
- 학생이 봤을 때 부담스럽거나 감시받는 느낌이 들지 않는가?
- 부모가 봤을 때 불안 조장보다 안심과 판단에 도움이 되는가?
- 새로 띄우는 확인, 선택, 입력 보조 UI를 브라우저 기본 alert/confirm/기본 선택창으로 처리하고 있지 않은가?
- 확인, 선택, 입력 보조 UI는 앱 안의 모달 또는 바텀시트로 대상과 영향을 함께 설명하는가?

## 권장 화면 이름

백오피스식 이름 대신 생활 장면 중심의 이름을 사용한다.

- `공부 스케줄 관리` 대신 `오늘`
- `일정 관리` 대신 `하루 흐름`
- `알림 관리` 대신 `약속 알림`
- `통계 대시보드` 대신 `하루 마감`
- `사용자 관리` 대신 `가족 설정`
- `완료 처리` 대신 `끝냈어요`

## Codex 작업 지시 기본 문구

화면 또는 기능을 구현할 때는 다음 지시를 함께 적용한다.

```text
그룹웨어/백오피스 스타일 UI로 흐르는 것을 피한다.
테이블, 관리 메뉴, CRUD 중심 화면을 기본값으로 삼지 않는다.
학생과 부모가 실제 생활 중 사용하는 모바일 우선 앱 경험으로 설계한다.
첫 화면은 데이터 목록이 아니라 현재 상태, 다음 행동, 남은 시간 판단을 보여준다.
이 화면을 관리자가 쓰는 화면처럼 만들면 실패한 것이다.
사용자가 앱을 켰을 때 3초 안에 지금 무엇을 해야 하는지 알 수 있어야 한다.
웹앱으로 구현하더라도 이후 모바일 앱 전환을 전제로 하고, 계산/알림/데이터 접근 로직을 UI에서 분리한다.
```

## 구현 우선순위

기능은 데이터 관리 순서가 아니라 사용자 장면 순서로 만든다.

1. 학생이 앱을 열고 지금 할 일을 확인한다.
2. 학생이 공부를 시작하고 진행 상태를 본다.
3. 놀이/휴식 종료 전에 부드러운 알림을 받는다.
4. 늦어졌을 때 회복 가능한 계획을 제안받는다.
5. 하루 마감에서 오늘을 정리한다.
6. 부모가 필요한 수준의 요약과 개입 필요 여부를 확인한다.
7. 부모 또는 학생이 계획을 조정한다.
8. 시험, 수행평가, 암기 루틴 같은 장기 목표를 월간, 주간, 일간 계획으로 자동 분해한다.

## 장기 계획 원칙

장기 계획 기능도 관리 페이지처럼 만들지 않는다.
학생에게는 `한 달 계획표 전체`보다 오늘의 작은 행동과 이번 주의 흐름을 우선 보여준다.
부모에게는 과목별 세부 표보다 계획이 현실적인지, 특정 과목이 과하게 밀리지 않는지, 이번 주 조정이 필요한지를 먼저 보여준다.

- 시험 일정은 과목과 시험일을 기준으로 등록한다.
- 시험 대비기간은 기본적으로 시험 한 달 전부터 시작하되 조정 가능하게 한다.
- 과목별 총 공부량을 주간, 일간으로 나눈다.
- 시험 전이 아닌 기간에는 평일 루틴과 반복 암기 루틴을 중심으로 계획한다.
- 장기 계획에서 생성된 오늘의 공부도 학생 화면에서는 일반 `지금 할 일`처럼 자연스럽게 보이게 한다.
- 장기 계획표를 전면에 두지 말고 `이번 주`, `오늘`, `다음 행동`으로 압축해서 보여준다.

## 대표 계획 원칙

- 한 달 계획은 시험 4주 전, 3주 전, 2주 전, 1주 전으로 나누고 단계별 목표와 강도를 다르게 둔다.
- 시험 4주 전은 개념 빈틈 확인과 무너지지 않는 루틴 만들기를 우선한다.
- 시험 3주 전은 문제풀이 시작을 우선한다.
- 시험 2주 전부터는 시험 모드로 전환해 시험범위 회독, 오답 반복, 암기 회독을 우선한다.
- 시험 1주 전은 암기, 오답, 교과서, 예상문제 중심으로 판단을 줄인다.
- 주간 계획은 하루 실패를 판단하는 도구가 아니라 주간 총량과 보정을 관리하는 현실 조정 장치다.
- 일일 계획은 시간표보다 필수, 추가, 남으면 미션 방식으로 제시한다.

## 제품 톤

앱의 톤은 잔소리, 감시, 처벌이 아니라 동행, 회복, 약속을 중심으로 한다.

나쁜 예:

```text
공부 시작 시간이 지났습니다. 부모님께 알립니다.
```

좋은 예:

```text
조금 늦었지만 아직 괜찮아요. 지금 수학 20분부터 시작하면 오늘 계획을 회복할 수 있어요.
```
